# research-graph

[![CI](https://github.com/crasavella04/research-graph/actions/workflows/ci.yml/badge.svg)](https://github.com/crasavella04/research-graph/actions/workflows/ci.yml)

`research-graph` — учебный проект курса «Разработка на Python и инженерия данных», который развивается в течение семестра.
Проект решает задачу анализа тональности пользовательских отзывов о доступности мобильных приложений: как люди с особыми потребностями оценивают удобство приложений и что им мешает.

Основа проекта — датасет [Accessibility User Reviews](https://www.kaggle.com/datasets/intelai/dataset-accessibility-user-reviews). Он содержит отзывы пользователей о доступности приложений с метками тональности.

## Требования

- Python 3.12+
- [uv](https://docs.astral.sh/uv/getting-started/installation/)
- Git

## Установка

```bash
git clone https://github.com/crasavella04/research-graph.git
cd research-graph
uv sync
```

`uv sync` сам поставит нужную версию Python (из `.python-version`), создаст `.venv`
и установит зависимости строго по `uv.lock`.

Создайте локальный файл настроек из шаблона (необязательно — без него используются значения по умолчанию):

```bash
cp .env.example .env
```

## Конфигурация

Настройки читаются из переменных окружения с префиксом `RG_` или из файла `.env` в текущей директории.
Переменные окружения имеют приоритет над `.env`. Файл `.env` не коммитится.

| Переменная | Описание | По умолчанию | Ограничения |
|---|---|---|---|
| `RG_GITHUB_TOKEN` | Токен GitHub API. В выводе CLI всегда маскируется | не задан | — |
| `RG_DATA_DIR` | Директория для данных проекта | `data` |  |
| `RG_LOG_LEVEL` | Уровень логирования | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` (регистр не важен) |
| `RG_LOG_FORMAT` | Формат логов: текст или одна JSON-строка на запись | `text` | `text`, `json` (регистр не важен) |
| `RG_REQUEST_TIMEOUT` | Таймаут HTTP-запросов, секунды | `10.0` | больше 0 и не больше 300 |
| `RG_MAX_CONCURRENCY` | Максимум одновременных запросов | `4` | от 1 до 64 |

## Использование

Список команд:

```bash
uv run rg --help
```

Версия пакета:

```bash
uv run rg version
```

```text
0.1.0
```

Проверка конфигурации — загружает настройки, настраивает логирование и печатает сводку:

```bash
uv run rg check-config
```

```text
github_token:    not set
data_dir:        /path/to/research-graph/data
log_level:       INFO
log_format:      text
request_timeout: 10.0
max_concurrency: 4
```

Если токен задан, он выводится только в маскированном виде, например `ghp_****abcd`.

Логи пишутся в stderr. Со структурным форматом каждая запись — одна JSON-строка,
которую удобно разбирать инструментами вроде `jq` или систем сбора логов:

```bash
RG_LOG_FORMAT=json RG_LOG_LEVEL=DEBUG uv run rg check-config
```

```text
{"timestamp": "2026-09-27T13:26:21.265711+00:00", "level": "DEBUG", "logger": "research_graph.cli", "message": "Settings loaded"}
github_token:    not set
...
```

Дополнительные поля передаются через `extra` и попадают в JSON как отдельные ключи:
`logger.info("loaded", extra={"rows": 1000})`.

При некорректном значении команда завершается с кодом 1 и объясняет, что не так:

```bash
RG_MAX_CONCURRENCY=0 uv run rg check-config
```

```text
Invalid configuration:
1 validation error for Settings
max_concurrency
  Input should be greater than or equal to 1 [type=greater_than_equal, input_value='0', input_type=str]
```

## Разработка

### Frontend: React + TypeScript

Запустите backend по инструкции ниже. В другом терминале:

```powershell
cd frontend
npm ci
npm run dev
```

Откройте [интерфейс](http://127.0.0.1:5173). Требуется Node.js 22+.
Vite перенаправляет запросы `/api` на backend по адресу `127.0.0.1:8000`.
Если порт 5173 занят, dev-сервер сообщит об ошибке, не переходя на другой порт.
Для другого адреса backend задайте VITE_API_URL в `frontend/.env.local`
и добавьте origin интерфейса в настройки CORS backend.

В интерфейсе три раздела:

- **Анализ отзыва** — предсказание, выбор правильного класса и запись feedback.
  Можно добавить новый размеченный пример, даже если модель ещё не загружена.
- **Обучение** — синхронное переобучение, параметры, метрики, матрицы ошибок
  и переход от ошибочного предсказания к форме исправления. Пока запрос
  выполняется, интерфейс блокирует действия и показывает время ожидания.
- **Модели** — сохранённые версии и первоначальная загрузка пары файлов
  model.joblib / metadata.json, если моделей на диске ещё нет.

Проверка frontend из каталога `frontend`: `npm test` и `npm run build`.
Сборка создаётся в `frontend/dist/`. Для локальной проверки сборки используйте
`npm run preview`; для размещения на другом сервере нужно настроить прокси
`/api` или указать VITE_API_URL перед сборкой. Артефакты сборки не коммитятся.

### Backend: FastAPI

Запуск из корня проекта (один процесс, порт 8000):

```bash
uv run uvicorn research_graph.backend.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Документация и ручная отправка запросов: [Swagger UI](http://127.0.0.1:8000/docs).
Модель при старте выбирается из последнего сохранённого каталога в `artifacts/`.
При отсутствии модели сервис запускается; `/health` и `/predict` возвращают 503.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/health` | Состояние, версия активной модели, признак обучения |
| POST | `/predict` | JSON с `text`; ответ: criticality, label, confidence |
| GET | `/models` | Список сохранённых моделей, параметры и доступные метрики |
| POST | `/load` | Первоначальный импорт готовой модели; multipart-поля `model`, `metadata` |
| POST | `/feedback` | JSON с `text` и `label`; добавление/исправление обучающего примера |
| POST | `/train` | Синхронное объединение данных, разбиение, обучение, оценка и активация |

`/predict` принимает непустой текст до 10 000 символов; версия модели передаётся
в `X-Model-Version`. Confidence берётся из модели и не является калиброванной
гарантией правильности. Классы: no_issue → null, low → 0, medium → 1, high → 2.

`/load` принимает `model.joblib` и `metadata.json` из команды `rg ml train`.
При наличии модели на диске возвращает 409; файлы проверяются до активации.
По умолчанию размер модели ограничен 50 MiB, metadata — 1 MiB (превышение: 413).
Импортируйте только доверенные joblib-файлы: их загрузка может выполнять Python-код.
Сервис предназначен для локального использования одним пользователем.

При первом `/feedback` или `/train` исходный размеченный CSV из
`data/processed/audit-v1/review.csv` импортируется в `data/datasets/dataset-.../reviews.csv`.
При его отсутствии нужно настроить путь начального CSV; требуются столбцы text
и label, допустимые классы и отсутствие конфликтующих дубликатов.
`feedback.csv` находится рядом с актуальным `reviews.csv`. Нормализованные
повторы обновляют метку в feedback, новые тексты добавляются. Предсказания
автоматически не записываются в обучающие данные.

`/train` принимает необязательный JSON:

```json
{"seed": 42, "c": 1.0, "max_iter": 1000}
```

Запрос ожидает полного завершения и возвращает 201 с версиями модели/датасета,
длительностью, размерами выборок, метриками и построчными предсказаниями validation/test.
Обучение выполняется в синхронном обработчике вне event loop. Другие endpoints
не блокируются; повторное одновременное обучение получает 409, чтобы не перезаписывать
результаты. Настройте таймаут HTTP-клиента не менее 120 секунд; разрыв соединения
сам по себе не отменяет работу обработчика. `/train/{job_id}` и фоновой очереди нет.

Feedback имеет приоритет над исходной меткой при совпадении нормализованного текста.
Перед обучением заново вычисляются группы похожих отзывов. Недостаток классов или
противоречащие метки близких текстов дают 422. При сбое сохраняются прежние модель,
актуальный датасет и feedback. При успехе фиксируется следующая версия датасета,
активируется новая модель; старые версии остаются. Изменения feedback, поступившие
после снимка данных, переносятся в feedback новой версии для следующего обучения.
Пути актуальных версий хранятся в `data/backend_state.json`, базы данных нет.

Настройки API в `.env` (JSON-массив для CORS):

```dotenv
RG_API_ARTIFACTS_DIR=artifacts
RG_API_INITIAL_DATASET=data/processed/audit-v1/review.csv
RG_API_CORS_ORIGINS=["http://localhost:5173","http://127.0.0.1:5173"]
RG_API_MAX_MODEL_BYTES=52428800
```

Каталог данных задаётся общей настройкой проекта. Вторая копия сервера с теми же
каталогами не поддерживается: файловые операции согласуются внутри одного процесса.

### Проверка API в Postman

Импортируйте [коллекцию](postman/research-graph.postman_collection.json) через
Postman → Import. В Variables задайте `baseUrl` (по умолчанию localhost:8000).
В папке основного сценария запросы идут в порядке: health → models → predict →
feedback → исправление feedback → train → проверка новой модели.
Проверки находятся во вкладке Tests/Post-response. Запрос `/train` действительно
обучает и создаёт новые версии; feedback изменяет локальный файл данных.

Папка первоначальной загрузки используется только если моделей нет на диске.
Для multipart полей `model` и `metadata` выберите локальные файлы через Select Files,
либо задайте абсолютные пути в переменных `modelFile` и `metadataFile`.
Postman может потребовать разрешить доступ к файлам вне своей рабочей директории.
С уже существующей моделью `/load` ожидаемо возвращает 409. Если модели нет,
сначала выполните загрузку либо `/train`, затем основной сценарий предсказаний.
В папке Validation находятся запросы с ожидаемыми ошибками 422.

### ML: оценка модели (этап 5)

После обучения сохранённой модели:

```bash
uv run rg ml evaluate
```

Команда загружает `artifacts/baseline-v1/model.joblib` и оценивает validation
и test из `data/processed/split-v1/` без переобучения. Проверяются SHA-256 модели
и обучающего CSV, отсутствие пересечения ID, групп и нормализованных текстов
между всеми тремя выборками. Существующие результаты не перезаписываются.

В `artifacts/baseline-v1/evaluation/` сохраняются:

- `report.json`, `report.md` — Accuracy, Precision/Recall/Macro-F1, метрики каждого
  класса и сравнение с предсказанием самого частого класса из train;
- `validation_confusion_matrix.csv`, `test_confusion_matrix.csv` — матрицы ошибок:
  строки обозначают истинные классы, столбцы — предсказанные;
- `validation_predictions.csv`, `test_predictions.csv` — тексты, истинные и
  предсказанные классы, признак правильности и вероятность предсказанного класса
  из модели (это не калиброванная гарантия правильности).

Precision и Recall в общей сводке усредняются по четырём классам (macro), как F1.
Неопределённые значения при нулевых знаменателях принимаются равными 0.
Для другой модели/версии данных или повторного отчёта укажите пути:

```bash
uv run rg ml evaluate --model-dir artifacts/baseline-v1 --split-dir data/processed/split-v1 --output artifacts/baseline-v1/evaluation-v2
```

Текущая разметка предназначена для проверки функциональности. Полученные метрики
показывают согласованность с этими метками; независимая оценка критичности
потребует отдельной проверенной выборки. Test не следует использовать для
подбора параметров. Матрицы и метрики можно посмотреть без отдельного сервера.

### ML: обучение базовой модели (этап 4)

После подготовки `data/processed/split-v1/train.csv` запустите:

```bash
uv run rg ml train
```

Команда обучает Pipeline `TF-IDF + Logistic Regression` только на `train.csv`.
Используются слова и пары слов, до 50 000 признаков, без удаления стоп-слов
(важно сохранять отрицания). Классификатор использует `class_weight=balanced`.
Validation и test на этом этапе не читаются; оценка метрик — следующий этап.
Текущие выборки предназначены для проверки функциональности.

Результаты сохраняются в `artifacts/baseline-v1/`:

- `model.joblib` — обученный векторизатор и классификатор в одном Pipeline;
- `metadata.json` — версия модели, классы, соответствие criticality,
  параметры, seed, версии библиотек, распределение обучающих меток и SHA-256
  обучающего CSV и модели.

Для повторного обучения укажите новый каталог версии:

```bash
uv run rg ml train --source data/processed/split-v1/train.csv --output artifacts/baseline-v2 --seed 42 --c 1.0 --max-iter 1000
```

Существующие модели не перезаписываются. При ошибке входных данных или
несходимости классификатора готовая версия модели не создаётся.
Для загрузки Pipeline используйте `joblib.load("artifacts/baseline-v1/model.joblib")`;
он принимает список текстов в `predict` и `predict_proba`, порядок столбцов
вероятностей задаёт `classes_`. Для загрузки нужны установленные зависимости
проекта; версии окружения записаны в metadata. Предполагаемый язык — английский.
Каталог `artifacts/` исключён из Git.

### ML: аудит и подготовка данных (этапы 1–3)

Исходный CSV положите в `data/raw/accessibility_reviews.csv`.
Данные исключены из Git. ML-команды работают локально, не используют LLM и
пока не обучают модель; дополнительных зависимостей не требуется.

```bash
uv run rg ml audit --source data/raw/accessibility_reviews.csv
```

В `data/processed/audit-v1/` появятся:

- `audit.json` — столбцы, пропуски, существующие метки, дубликаты и SHA-256 источника;
- `cleaned.csv` — уникальные непустые тексты с идентификаторами групп;
- `review.csv` — файл ручной разметки без придуманных меток критичности.

Исходник не изменяется. Очистка нормализует Unicode и пробелы, сохраняя
пунктуацию и отрицания. Исходный `cleanText` не используется: для классификации
важно не потерять контекст. Повторяющиеся тексты объединяются; близкие тексты
остаются отдельными строками одной группы.

Можно предварительно предложить метки английских отзывов по консервативным
текстовым правилам (это не обученная модель и не ручная проверка):

```bash
uv run rg ml annotate --review data/processed/audit-v1/review.csv
```

Команда сохраняет резервную копию `review.before-rules-v1.csv`, записывает
предложения в `label` и обоснования в `notes`; спорные отзывы остаются без класса.
Заполненные человеком поля сохраняются. Новые строки остаются `reviewed=false`:
автоматические метки нельзя выдавать за независимую проверенную разметку.
Результат подсчитывается в `annotation_report.json`.

Проверьте и заполните `review.csv` по [правилам разметки](docs/annotation.md), затем:

```bash
uv run rg ml prepare --review data/processed/audit-v1/review.csv
```

Команда создаёт `data/processed/split-v1/{train,validation,test}.csv` и
`manifest.json` с распределением классов, seed и контрольными суммами.
Используются только проверенные человеком строки; при недостатке классов
команда завершится с понятной ошибкой, не создавая фиктивных выборок.
Сходные отзывы не распределяются между разными выборками.
Существующие выходные каталоги не перезаписываются: для новой версии укажите
`--output`; для разбиения другого аудита также укажите `--audit-dir`.

Факты первичного аудита локального датасета приведены в
[отчёте](docs/dataset_audit.md). Качество модели пока не оценено.

Тесты с отчётом о покрытии:

```bash
uv run pytest
```

Линтер и проверка форматирования:

```bash
uv run ruff check .
uv run ruff format --check .
```

Проверка типов:

```bash
uv run mypy
```

Хуки pre-commit (ruff, ruff-format, mypy и базовые проверки) запускаются при каждом коммите.
Установка и ручной прогон по всем файлам:

```bash
uv run pre-commit install
uv run pre-commit run --all-files
```

Те же проверки выполняет CI в GitHub Actions на каждый push в `main` и pull request:
тесты гоняются на Python 3.12 и 3.13 под Ubuntu и Windows.
